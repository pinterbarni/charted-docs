    ⭐ HR¶

    This page is a shortcut through the thesis for recruiters and hiring managers.The thesis was submitted at ELTE, everything works as it should.

    Instead of reading a hundred pages, pick a question below, open it.

    The 30-second version¶

    Charted is a mobile app for hikers with social features: plan a route, record the hike, then share it and follow other hikers. I built all of it, from a full design system in Figma to the React Native app and the NestJS backend, with the architecture designed for microservices from the start, so routing, map tiles and sign-in already run as separate services. And it is not just a demo on a laptop: it is deployed to a pre-production environment on servers I set up myself.

    I shaped the thesis scope around what the thesis evaluates, so I spent less time on things like sophisticated testing than I would in other projects.

    I lost only a single point in the evaluation of my thesis work, then defended it successfully.

    What I took away¶

    Collaboration matters. The depth I admire in professional systems comes from people building them together, everyone bringing their own expertise and since this project I see the systems I've worked with in a completely different way.

    Design and thinking¶

    How decisions were made, and how the interface was designed.

    ...if Barni put in a complex thought process

    Short answer: yes. The decisions are documented together with the reasoning and the trade-offs in the documentation.

    The architecture pivot

    The first plan was microservices: a Backend-for-Frontend in front of separate routing, map tile and domain services, talking over a Redpanda pipeline. Early on it became clear that running and wiring all of that would eat the time budget of the thesis, on ARM servers where every tool had to be checked for compatibility. The backend became a modular monolith instead, built so its modules can be split into services later. Routing (Valhalla) and map tiles (Martin) stayed separate services, because there the separation pays for itself.

    Working with a beta dependency

    Halfway through, the stable MapLibre release only supported Expo SDK 54, while the app had been built on SDK 55 for months. Rolling back was more expensive than the risk, so the app moved to the MapLibre 11 beta. I would have favored rolling back if It was for an existing, contractual client.

    Where to look

    • Architectural decisions: microservices versus a modular monolith.
    • Technology choice: why each tool was picked.
    • Challenges: what went wrong and how it was solved.

    Why it matters: documenting decisions is a value.

    ...if Barni can use Figma

    Short answer: yes. The whole interface was designed in Figma before a line of app code was written, by hand and without AI tools.

    The process went from studying existing map apps, through paper sketches, a type system and a color palette, to a parameterized component library: buttons from primary to quaternary level, small components composed into larger UI elements, and those into full screen prototypes, with a consistent 16 design system, applicable for the web later on.

    Used parameters and prototypes to mock the components and views.

    Where to look

    • The Figma file: the original design, open to view
    • UI and UX design: from sketches to components, in depth.

    Why it matters: designing wire-frames, then design first meant the UX became more coherent, it was easier to write down the design system and by this, to change the design later.

    ...if Barni writes maintainable code

    Short answer: yes. The codebase follows written conventions, so the next developer does not have to guess.

    • Documented: every public service method, controller and injectable class has JSDoc with @param, @returns and @throws, which feeds the generated Compodoc documentation. We also have a full Swagger documentation.

    Where to look

    • Code quality (Backend example): conventions and tooling.
    • Modules: what each backend module does.
    • State management: the four stores.

    Why it matters: can and do follow conventions, I understand that code is read more than it's written, it's also a good practice to prepare for tomorrow's AI-driven development practices.

    Diagrams¶

    Flows, data and deployment, drawn as code.

    ...if Barni used sequence diagrams

    Short answer: yes. Authentication, token refresh and the profile upsert are all Mermaid sequence diagrams, and each one comes with a table that explains every step in words.

    This is the authentication flow, from signing in to the first protected API request, drawn live from its source file:

    KC-->>App: 4. access_token + refresh_token

    App->>BFF: 5. API request (Bearer access_token)
    BFF->>KC: 6. JWKS request (public key, cached)
    KC-->>BFF: 7. Public key, cached by the BFF
    BFF->>BFF: 8. Signature and expiry check
    BFF->>DB: 9. Business logic
    DB-->>BFF: 10. Result
    BFF-->>App: 11. JSON response
    Step From To What happens
    1 App Keycloak Requests an authorization code with a PKCE code_challenge
    2 Keycloak App Returns the authorization code
    3 App Keycloak Exchanges the code and the code_verifier for tokens
    4 Keycloak App Returns the access_token and the refresh_token
    5 App BFF Sends an API request with the access_token as a Bearer token
    6 BFF Keycloak Requests the public key set (JWKS), unless it is already cached
    7 Keycloak BFF Returns the public key, which the BFF caches
    8 BFF BFF Checks the token's RS256 signature and expiry
    9 BFF PostgreSQL Runs the business logic
    10 PostgreSQL BFF Returns the result
    11 BFF App Sends the JSON response

    Where to look

    • Navigation: the screen structure in detail
    • Authentication: sequence diagrams with step-by-step tables

    Why it matters: a diagram shows the order of events, the table gives the details, and it's easier to digest for most of the stakeholders. Together teh diagram and the descriptive table let a reviewer follow a flow across four systems without opening the code. I picked up this habit from a great manager, and it has stuck with me ever since.

    A few of the decisions behind it:

    • The identity provider's ID is the primary key: a user's ID is the sub claim of their Keycloak token, so the backend reads it straight from every authenticated request.
    • Heavy data is kept apart: avatars live in their own table, because a base64 image can be hundreds of kilobytes and most profile requests do not need it.
    • Totals are stored, not recalculated: a user's total distance grows with every saved trail, so showing their level takes one field read instead of an aggregate query.
    • GPS tracks are stored as JSONB: a single hike can record thousands of points. One queryable JSONB column keeps them together in one row instead of growing a huge separate table.
    • Blocking works both ways: a block is stored as one directed pair, and every query checks both directions, so neither user sees the other's content.
    • One table for all reports: a target_type field tells whether a report is about a user or a trail, so new report types need no new table.

    Where to look

    • Data model: every table and the reasoning behind it

    Why it matters: choices like these decide how fast the app stays as the data grows. Designed purposefully.

    Backend and security¶

    The API, and who can access what.

    ...how many endpoints Barni wrote, and how RESTful they are

    Short answer: 35 endpoints across the profile, trail, social, route, report and health areas, plus 2 proxy routes to the routing engine and the map tile server.

    pie showData title Endpoints by HTTP method
    "GET" : 20
    "POST" : 8
    "DELETE" : 6
    "PATCH" : 3
    • Resources: one resource, several methods. /api/profile/me is read with GET, created on first sign-in with POST and edited with PATCH.
    • Partial updates use PATCH: only the changed fields are sent.
    • Documented: Swagger (OpenAPI) is generated from @nestjs/swagger decorators and served at /api/docs.
    • Tested as code: the requests live in Bruno collections, plain text .bru files kept in the repository next to the code. (Bruno is an API client, just like Postman.)
    • One door policy: the mobile app never calls Valhalla or Martin directly. Every request goes through the backend, which keeps keys and caching on the server.

    Where to look - API endpoints: every endpoint, grouped by controller - Proxy modules: how the routing and tile proxies work

    Why it matters: a predictable API is one that a frontend developer can use from the docs alone, without asking the backend developer.

    ...if Barni takes security seriously

    Short answer: yes, from the sign-in flow down to the network.

    • No passwords in the app: sign-in uses Keycloak with the OAuth2 authorization code flow and PKCE, the standard for mobile apps.
    • No secrets in the backend: tokens are validated against Keycloak's public keys (JWKS), cached for five minutes, so no shared secret is stored and most requests need no call to Keycloak.
    • Secure by default: a global JWT guard protects every endpoint, and only the health check is public. Rate limiting is on.
    • Tokens stored safely: the app keeps them in the device's secure storage and refreshes them automatically.
    • Small attack surface: only the edge server is public, behind nginx with TLS. The servers talk to each other only through encrypted tunnels on a Tailscale mesh VPN.
    • Separated networks: the servers run on their own isolated network, while the development machine and every other device stay on the guest network.
    • Separated environments: development and pre-production each have their own configuration, database and secrets, so testing never touches real user data and a development key never works on the servers.
    • Monitored: the public health endpoint is watched by a self-hosted Uptime Kuma instance, so downtime is noticed right away.
    • Secrets stay out of Git: they are never committed. Each repository has separate .env.development, .env.preprod and .env.prod files, which Git ignores, and a .env.example that lists the variables without values.
    • Secrets stay out of AI tools: no key, password or token was ever shared with an AI assistant.

    Where to look

    • Authentication: the sign-in and token refresh flows
    • Infrastructure: the two servers and the network around them

    Why it matters: security is a core value of any production system, so I built it in from the start, as thoroughly as I could.

    ...if Barni thinks about the rights of different stakeholders

    Short answer: yes. As a single developer, I was the tester, developer and operator at once, so separating rights in practice would only have added administrative overhead. But the system is designed for the day more people join, with one principle: everyone gets access to what their job needs, and nothing more.

    In place today

    • Hikers: every user signs in through Keycloak, and their identity comes from the token, so the backend always knows whose data a request touches. Users decide whether a trail is shared, and blocking hides both users' content from each other.
    • Identity administration: user accounts, passwords and sessions are managed in Keycloak's own admin console, separate from the app and its database.
    • Separate environments: development has its own configuration, database and secrets, so day-to-day development never needs access to the pre-production servers.

    Already prepared for, so it is easy to add later

    • Moderators: reports are already stored with a moderator response field, and there is an admin endpoint for them. A dedicated admin interface with role checks comes next.
    • Testers: access to the app and its test accounts on the pre-production system, without servers, configuration or secrets.
    • Developers and operators: developers work in their own environment, and server access stays with the people who run the system.
    • Audit logging: the backend already writes structured logs, and Keycloak can record sign-in and admin events, so who did what, and when, can be traced once more people have access.

    These are only a few examples. The same approach of separate roles, least privilege and traceable access is what enterprise-level identity and access management is built on.

    Where to look

    • Authentication: how identity reaches the backend
    • Modules: the reports module and its admin endpoint
    • Future work: the planned admin interface

    Why it matters: in a real enterprise level system, not everyone should see everything. Knowing when access control is worth its cost, and designing so it can be added cleanly later, is part of building a system that scales with its team.

    Shipping and operations¶

    Servers, environments, containers and version control.

    ...if Barni can ship to production

    Short answer: yes. Charted runs on self-hosted hardware, and the API and sign-in are live at api.charted.hu and sso.charted.hu.

    • Edge server (Janus): nginx as a reverse proxy with TLS, routing each domain to the right service.
    • Application server (Vesta): Docker Compose with the NestJS backend, PostgreSQL with PostGIS, Keycloak with its own database, Valhalla for routing and Martin for map tiles, on separate Docker networks.
    • Mobile builds: three EAS profiles, for development, internal testing and production, with the build number increased automatically.
    • Health checks: Docker Compose watches a public health endpoint to know when the backend is up.

    The first deployment taught a few lessons: the database schema had to be created on the first start, TLS was needed earlier than expected, and PostgreSQL needed a community image to run on ARM.

    Where to look

    • Docker: every service and where it runs
    • Challenges: what went wrong on the first deployment

    Why it matters: this project runs on set up and maintained hardware.

    ...if Barni uses version control

    Short answer: yes, every day. Git history was not part of the submitted thesis, because the .git got removed from the submitted source, with the .env files. If you want to see a simplified example, check out the VC of this documentation.

    The charted-docs repository follows GitHub flow:

    • a short-lived branch for every feature or fix, merged with --no-ff, so each feature stays visible in the history
    • small commits with one idea each, written as Conventional Commits (feat:, fix:, docs:, ci:)
    • versioned documentation with mike: latest is the living version, and 1.0.0 will freeze the submitted text

    Also worked with Git-flow, with its develop, release and hotfix branches. I usually pick the model that fits the release cycle, nowadays lean toward using the least for hobby projects.

    Where to look

    • Commit history: the branches and merges, as they happened

    Why it matters: documentation is key of a manageable codebase.

    ...if Barni uses different environments

    Short answer: yes, development, production and pre-production were planned for this project.

    In development for example, the backend and its database run on the developer machine, while the heavy services (Keycloak, Valhalla and Martin) stay on the Vesta server and are reached over Tailscale. This is the development setup, drawn live from its source file:

    Development Production
    Backend Runs locally with hot reload Docker Compose on the Vesta server
    Database Local PostgreSQL, schema created automatically PostGIS container, schema sync turned off
    Configuration .env.development .env.production
    Mobile build EAS development profile with the dev client EAS production profile, release APK
    Backend address A local address https://api.charted.hu

    A third EAS profile, preview, builds a release version for internal testing before production.

    • No secrets in Git: .env files are ignored, and every repository has a .env.example that lists the variables without values.
    • Nothing sensitive in the app: variables with the EXPO_PUBLIC_ prefix end up in the app bundle, so they never hold secrets.
    • Safe defaults in production: automatic schema changes are off, and turning them on for the first start is a deliberate, documented step.

    Where to look

    • Development environment: how to run everything locally
    • Configuration: every environment variable and what it does
    • Infrastructure: development and production deployment diagrams

    Why it matters: keeping environments apart means experiments never touch real users' data, and production behaves the same way every time it starts.

    ...if Barni treats documentation like code

    Short answer: yes, and you are reading the proof. This site is built, checked and deployed like software.

    • Built from source: Material for MkDocs, with dependencies pinned by uv.
    • Bilingual: Hungarian and English from the same structure, with mkdocs-static-i18n.
    • Versioned: mike publishes latest and, later, the frozen 1.0.0 to GitHub Pages.
    • Checked on every push: reusable GitHub Actions workflows build the site, check every link, spellcheck both languages with cspell, and lint the shell scripts with ShellCheck.
    • Measured: scripts report how many pages are finished and described in each language.
    • Diagrams as code: Mermaid and PlantUML sources, rendered during the build.

    Where to look

    • The repository: the workflows, scripts and configuration

    Why it matters: broken links and typos are caught by a machine before a reader finds them. Docs shall stay coherent and help stakeholders, not confuse them.

    ...if Barni can work with Docker images

    Short answer: yes. Every backend service runs as a container, built or chosen to run natively on the ARM64 processors of the Raspberry Pi servers.

    Note

    This part could have been built more thoroughly, for example with a fully automated deployment pipeline, and documented in more depth. I kept both simple on purpose, because the thesis evaluation did not award points for them.

    Service Image Notes
    NestJS backend Built from its own Dockerfile An ARM64 image, built and started with Docker Compose
    PostgreSQL with PostGIS imresamu/postgis:16-3.4 A community image, because the official one does not run natively on ARM64
    Keycloak and its own PostgreSQL Official images On a separate Docker network from the application
    Martin Official image Serves map tiles straight from the PostGIS database
    Valhalla Official image Plans walking routes
    • Networks keep services apart: the backend and its database share one Docker network, and Keycloak with its own database runs on another, so a problem in one cannot reach the other's data.
    • Health checks: Docker Compose watches the backend's public health endpoint to know when the container is really up.
    • One command to deploy: the backend is rebuilt and restarted on the server with a single docker compose up -d --build.
    • Data lives in volumes: the databases keep their data in Docker volumes, detached from the containers, so a container can be rebuilt, updated or replaced without losing anything.
    • Ready for automation: a self-hosted Drone CI server already runs next to the containers, and connecting it to an automated deploy pipeline is planned for the next version.

    Where to look

    • Docker: every container and the server it runs on
    • CI/CD: mobile build profiles and the backend deployment
    • Challenges: finding a PostgreSQL image that runs on ARM

    Why it matters: containers make every environment start the same way.

    AI¶

    Where AI was used, and how it was kept in check.

    ...if Barni uses AI responsibly

    Short answer: yes. AI is a tool with failure modes, so I measure it, review what it produces, and keep it away from anything it should not see.

    • Humans make the final call: every AI suggestion is reviewed, tested and committed by hand. Nothing goes into a repository unread.
    • Secrets never reach AI tools: no key, password or token was ever shared with an AI assistant.
    • Some work stays human by choice: the whole interface was designed in Figma by hand, without AI tools.
    • Measured, not trusted blindly: the English version of this site will come from an AI translation pipeline on AWS Bedrock. Two models translate the same text so their results can be compared, evaluations score the output, and every proposal is reviewed, with accepted and declined changes tracked.

    Work in progress

    The translation pipeline is being built right now. This answer will be updated as it grows.

    Why it matters: AI can ship confident mistakes. Measuring it and keeping a human in the loop is what makes it safe to use in real work, while keeping out sensitive data is crucial.

    ...if Barni used AI to develop the application

    Short answer: yes, as a tool. I used AI the way I would ask a senior developer on my team: for a second opinion, a quick lookup or to take over repetitive work, never to write the application for me. Every use was declared in the mandatory AI statement of the thesis.

    • Taking over repetitive work: converting SVG icons exported from Figma into app components, and turning a finished Markdown table into a LaTeX one.
    • A second opinion: checking whether the gamification level values were realistic, reviewing my code against clean code practices, and looking for redundant steps in the test cases.
    • A starting point to refine: suggesting a dark mode palette from my existing light colors, and a Keycloak theme from the app's styles. I reviewed and changed both before using them.
    • Quick lookups: CLI commands for moving files to the servers, LaTeX and PlantUML syntax, naming small components, and Hungarian equivalents of English technical terms.
    • Proofreading: I dictated parts of the thesis text, then asked AI to spot repetition and suggest clearer wording.

    What it did not do: the architecture, the backend, the app's features and the Figma design are my own work. The tools were ChatGPT, Gemini in Brave, Claude, and GitLens for a handful of commit messages, and I validated the result after every step.

    Note

    I kept AI to these roles because this was a university thesis, where the work had to show my own knowledge.
